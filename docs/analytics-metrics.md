# Метрики качества вопросов

Этот документ фиксирует пользовательский смысл показателей Candidate Check v1.1.0. Он нужен, чтобы интерфейс, API и эксплуатационные отчёты одинаково отвечали на два разных вопроса:

1. **Что фактически произошло?** — абсолютные счётчики и наблюдаемые доли.
2. **Какой вывод уже допустим?** — уровень достоверности, сигналы и рекомендация.

Маленькая выборка не скрывает факты. Она ограничивает уверенность вывода.

## Единица анализа

Для калибровки используются только exact facts (`analytics_facts_version = 1`) и по умолчанию последняя завершённая попытка кандидата в неизменяемой когорте:

```text
scoring_version + test_config_id + bank_revision + test_profile_id
```

Базовые и дополнительные вопросы не смешиваются. Основной quality-профиль рассчитывается по базовым предъявлениям; дополнительные показываются отдельно как recovery-выборка.

Синтетический `total_timeout_unshown` не считается предъявлением или результатом вопроса и не входит в quality, timing и анализ вариантов.

## Наблюдаемые счётчики

| Поле | Значение |
|---|---|
| `assigned` | вопрос назначен попытке |
| `presented` | сервер сделал вопрос текущим |
| `resolved` | предъявленный вопрос завершён ответом или тайм-аутом |
| `correct` | правильные результаты |
| `incorrect` | неправильные результаты без тайм-аутов |
| `timedOut` | тайм-ауты предъявленного вопроса |
| `submitted` | ответы кандидата без тайм-аутов |

Инварианты:

```text
presented <= assigned
resolved = correct + incorrect + timedOut
resolved <= presented
submitted = correct + incorrect
```

Проценты в UI всегда показываются вместе с числителем и знаменателем, например `18 из 30 · 60%`.

## Формулы

```text
presentationRate = presented / assigned
responseRate     = submitted / presented
completionRate = resolved / presented
successRate    = correct / resolved
timeoutRate    = timedOut / resolved
```

Время ответа (`average`, `median`, `min`, `max`) рассчитывается только по `answer_origin = submitted`. Тайм-ауты не подменяются лимитом в 30 секунд.

`medianSeconds` в UI называется «Типичное время». Сравнение с вопросами той же сложности допускается только при наличии не менее пяти сопоставимых peer-вопросов с timing-данными.

## Уровни достоверности

`n` — число реальных результатов (`resolved`) для выбранной роли вопроса и когорты.

| n | API level | Подпись в интерфейсе | Допустимый вывод |
|---:|---|---|---|
| `0–29` | `insufficient` | Мало данных | только факты; показывается, сколько результатов осталось до 30 |
| `30–49` | `early` | Первичный сигнал | предупреждения возможны, итоговая оценка качества ещё недоступна |
| `50–99` | `working` | Рабочая оценка | доступен индекс качества; discrimination ещё не рассчитывается |
| `100+` | `stable` | Стабильная оценка | доступна полная оценка при наличии остальных компонентов |

Границы включительны: `30`, `50` и `100` переключают уровень. API возвращает следующий gate и число недостающих результатов; клиент не вычисляет их самостоятельно.

## Ожидаемая доля верных

| Сложность | Ожидаемый диапазон |
|---|---:|
| `easy` | 75–95% |
| `medium` | 55–80% |
| `hard` | 30–60% |
| `expert` | 10–40% |

При `n >= 30` значение строго выше верхней границы создаёт сигнал `too_easy`, строго ниже нижней — `too_hard`. Значения на самой границе считаются соответствующими сложности.

## Сигналы

Сигнал объясняет наблюдаемое отклонение, но не является решением администратора.

| Сигнал | Условие |
|---|---|
| `sample_insufficient` | `n < 30` |
| `sample_early` | `30 <= n < 50` |
| `too_easy` | `n >= 30`, success rate выше диапазона сложности |
| `too_hard` | `n >= 30`, success rate ниже диапазона сложности |
| `high_timeout` | `n >= 30`, timeout rate не меньше 25% |
| `slow` | `n >= 30`, достаточно peers и медиана не меньше 1,5 медианы сложности |
| `negative_discrimination` | `n >= 100`, point-biserial меньше 0 |

Срочная аномалия может быть показана до quality gate как предупреждение, но не должна превращаться в уверенный статус «вопрос хороший».

## Индекс качества вопроса

Индекс включается при `n >= 50` и состоит из независимых компонентов:

| Компонент | Максимум |
|---|---:|
| Соответствие заявленной сложности | 30 |
| Здоровье тайм-аутов | 20 |
| Стабильность времени | 10 |
| Качество вариантов ответа | 20 |
| Разделяющая способность | 20 |

Отсутствующий компонент не нормализуется скрыто. API возвращает:

```text
earned / maxAvailable
partial = maxAvailable < 100
```

Поэтому `58 / 80` нельзя отображать как `73 / 100`. Интерфейс явно подписывает неполный индекс и перечисляет ещё недоступные компоненты.

Статус индекса при `n >= 50`:

```text
good    >= 75 и нет critical signal
observe 50–74
review  < 50 или есть critical signal
```

До `n = 50` status остаётся `insufficient`, даже если наблюдаемые проценты выглядят хорошо.

## Варианты ответа и discrimination

Распределение A/B/C/D строится по `canonical_selected_index` только для submitted-ответов. В API не передаются правильный индекс, текст вариантов или выбранный кандидатом raw-ответ.

Вариант считается работающим distractor при `n >= 50` и доле выбора не меньше 5%. Ровно 5% включается в расчёт.

Point-biserial discrimination:

- рассчитывается только для базовых вопросов;
- использует completed exact cohort и последнюю попытку кандидата;
- использует base rest-score без текущего вопроса и remedial;
- недоступна при `n < 100`, отсутствии обеих outcome-групп или нулевой variance;
- ограничена диапазоном `-1..1`.

## Рекомендации и решения администратора

Автоматическая рекомендация и ручное решение — разные сущности.

- при `n < 30`: `Накопить ещё N результатов`;
- при `30 <= n < 50`: допускается только осторожная рекомендация наблюдать или проверить конкретный ранний сигнал;
- `Оставить без изменений` запрещено при `n < 50`;
- при `n >= 50`: рекомендация следует из critical signals, тайм-аутов, discrimination и качества вариантов;
- ручное решение `keep / observe / disable_requested / new_revision_required` хранится отдельно и не переписывает банк вопросов.

## Поиск, сортировка и пагинация

Список вопросов фильтруется и сортируется на сервере до пагинации. Поддерживаемые параметры:

```text
q
qualityStatus
topic
difficulty
questionKind
sort=priority|timeout|success|sample|lastPresented|id
direction=asc|desc
cursor
limit
```

Ответ списка содержит `totalCount` по всей отфильтрованной выборке, summary по статусам и `nextCursor`. `totalCount` учитывает все активные фильтры. Summary сохраняет распределение статусов до применения `qualityStatus`, но после поискового запроса, когорты, темы, сложности, роли и уровня достоверности — благодаря этому карточки не исчезают при выборе одного статуса. По умолчанию используется приоритетный порядок: критические → проверить → наблюдать → мало данных → норма. Поиск не ограничивается уже загруженной страницей.

## Проверки контракта

Минимальный набор regression tests:

- границы `29/30/49/50/99/100`;
- запрет `keep` при `n < 50`;
- включительные границы expected ranges, timeout `25%`, distractor `5%` и slow `1.5×`;
- честный `earned / maxAvailable` без нормализации partial score;
- серверные search/sort/filter применяются до pagination;
- `totalCount`, summary и cursor относятся к одному и тому же фильтру;
- UI показывает числитель и знаменатель и не создаёт горизонтальный scroll на iPad portrait/landscape.
