# Управление банком вопросов

Начиная с v1.2.0 банк вопросов управляется из локальной административной панели. D1 хранит рабочее состояние и историю ревизий; `db/questions.json` используется только для первоначальной загрузки пустой базы. После первого bootstrap перезапуск приложения не откатывает изменения администратора к содержимому JSON-файла.

## Основные правила

- Содержимое опубликованного `question.id` неизменяемо.
- Изменение текста, контекста, вариантов ответа, правильного ответа, темы, сложности или `dedupeKey` создаёт новую редакцию с новым ID.
- Предыдущая редакция сохраняется для истории и аналитики, но становится неактивной.
- Активация и деактивация не переписывают содержимое вопроса и создают новую ревизию банка.
- Каждая операция сохраняет полный snapshot membership новой ревизии и запись аудита без PIN и содержимого admin cookie.
- Два открытых окна не могут незаметно перезаписать друг друга: mutation принимает ожидаемую ревизию и при конфликте требует обновить данные.

Такой workflow намеренно немного строже обычной формы редактирования. Он сохраняет воспроизводимость уже проведённых тестов: вопрос в старой попытке всегда означает тот же текст, категорию, сложность и ключ ответа, что и в момент тестирования.

## Работа в интерфейсе

1. Войти через `/admin/login` и открыть вкладку «Банк вопросов».
2. Найти вопрос по ID, тексту, теме или `dedupeKey`; при необходимости выбрать тему, сложность и состояние.
3. Нажать «Открыть», чтобы увидеть полный текст, контекст, варианты, правильный вариант, состояние и историю редакций.
4. Для нового вопроса выбрать «Добавить вопрос», заполнить поля и сохранить.
5. Для смыслового изменения выбрать «Создать редакцию». После сохранения новая редакция становится активной, старая — неактивной.
6. Для временного исключения без изменения содержания использовать переключатель активности.
7. После изменения проверить сводку готовности банка. Если квоты теста или remedial-резерв нарушены, операция отклоняется и рабочая ревизия остаётся прежней.

Правильный вариант показывается только в защищённой admin-панели. Analytics export по-прежнему не содержит текстов вариантов, правильных ответов, PIN, session token или Telegram payload.

## Валидация

Перед применением сервер проверяет всю будущую ревизию, а не только изменённую строку:

- ID — положительное целое число и не используется существующей редакцией;
- тема и формулировка непустые;
- сложность — `easy`, `medium`, `hard` или `expert`;
- от 2 до 5 непустых уникальных вариантов;
- правильный индекс находится в границах списка;
- длины prompt, context, choice и `dedupeKey` соответствуют общим лимитам;
- `contextType` и context задаются совместно;
- активные вопросы не создают явный или вероятный дубль без общего `dedupeKey`;
- пул сохраняет стартовые квоты и remedial-резерв.

Ошибка валидации возвращается как безопасный структурированный ответ. До успешной проверки D1 не изменяется и новая ревизия не создаётся.

## Конкурентные изменения и повтор запроса

Форма передаёт `expectedRevision`, полученный при загрузке банка. Если другая вкладка уже применила изменение, сервер отвечает `409 bank_revision_conflict`; администратор обновляет данные и повторно сравнивает изменения. Автоматическое «последняя запись победила» запрещено.

Повтор одного и того же запроса после потери сетевого ответа не должен создавать вторую редакцию или второй audit event. Клиент использует стабильный mutation key, а сервер возвращает уже созданный результат либо применяет операцию ровно один раз.

## Хранение и восстановление

В backup входят:

- текущий указатель ревизии банка;
- immutable-вопросы и полные membership snapshots;
- связи predecessor → successor;
- журнал операций и существующая review history.

`ops:backup:verify` проверяет внешние ключи, единственность текущего состояния, ссылки редакций и отсутствие разветвления цепочки successor. Restore восстанавливает эти таблицы вместе с остальной D1. Старые analytics facts и завершённые попытки не переписываются при создании новой редакции.

## Матрица приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Создание | Новый ID активен, revision изменён, snapshot и audit event созданы |
| Редакция текста/темы/сложности | Старый ID сохранён и выключен, новый ID активен, predecessor/successor связаны |
| Активация/деактивация | Содержание и ID прежние, revision и audit изменены |
| История | Видны revision, timestamp и тип операции без PIN/cookie |
| Некорректное поле или неготовый пул | `400`, D1 и текущая revision не изменены |
| Устаревшая `expectedRevision` | `409`, чужое изменение не перезаписано |
| Повтор mutation key | Возвращён тот же результат без второй редакции |
| Запрос без сессии / CSRF | `401` / `403`, состояние не изменено |
| Перезапуск | Текущая D1-ревизия и активность сохранены |
| Историческая аналитика | Старый ID и его факты остаются в старой ревизии |
| Analytics export | Нет choices, correct answer, PIN, cookie и Telegram payload |
