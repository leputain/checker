# Candidate Check

Candidate Check — локальное iPad-first приложение для первичного технического отбора кандидатов. Интерфейс работает на React 19, API — в Cloudflare Worker runtime через Vinext, данные — в project-local SQLite-совместимой D1.

Версия 0.5.1 делает тест устойчивым к reload, двойным нажатиям, рассинхронизации часов и кратким сетевым сбоям. Telegram получает обновляемую карточку прогресса, детали ошибок и итог теста через надёжную outbox, при этом недоступность Telegram не задерживает кандидата. Patch-релиз 0.5.1 также исправляет отображение фоновой графики и маскота при публикации в подпути `/candidate/`.

## Возможности v0.5.1

- старт без регистрации по имени кандидата;
- минимум 20 базовых вопросов: 5 простых, 7 средних, 7 сложных и 1 экспертный;
- общий серверный лимит 10 минут и 30 секунд на вопрос;
- случайная выборка из четырёх пулов сложности;
- дополнительный вопрос той же сложности после ошибки или таймаута;
- серверные scoring, verdict и deadlines без передачи правильных ответов в браузер;
- идемпотентное создание попытки через `startKey` и секретный token, на сервере хранится только SHA-256 hash token;
- идемпотентный ответ: двойной tap или повтор после сетевого сбоя не создаёт вторую запись;
- компенсация расхождения часов iPad через `serverNowMs`;
- восстановление активной попытки после reload и возврата Safari из background;
- обновляемая Telegram-карточка, отдельные сообщения об ошибках и итоговая сводка через D1 outbox;
- анонимный рейтинг только на экране результата;
- PWA manifest, standalone-режим, safe-area, Wake Lock и offline/reconnect-индикатор;
- доступные таймеры, touch targets от 44 px, keyboard focus, dialog и reduced-motion режим;
- управляемые миграции схемы, health endpoints, backup/restore и retention-команды.

## Модель оценки

| Уровень | Вес | Стартовая квота |
|---|---:|---:|
| Базовый (`easy`) | 1 | 7 |
| Средний (`medium`) | 2 | 7 |
| Сложный (`hard`) | 3 | 5 |
| Экспертный (`expert`) | 10 | 1 |

Двадцать стартовых вопросов дают `baseMaxScore = 46`. Правильный remedial-ответ возвращает баллы своего уровня, но итоговый score не может превысить этот максимум.

Verdict рассчитывается сервером:

- `PASS` → «Рекомендован»: score и accuracy не менее 70%;
- `REVIEW` → «Нужна проверка»: score не менее 50% или accuracy не менее 60%;
- `FAIL` → «Не рекомендован»: ниже порога `REVIEW`.

## Быстрый запуск

Требуется Node.js 22.13+.

```powershell
npm install
Copy-Item db/questions.example.json db/questions.json
npm run questions:validate
npm run dev -- --port 3001
```

Откройте URL из вывода dev-сервера. Локальная D1 хранится в игнорируемом каталоге `.wrangler/`.

## Telegram-конфигурация

В корне нужен локальный `tg_token.txt`, содержащий ровно один bot token и ровно один групповой `chat_id` формата `-100…`. Подписи и пробелы допустимы, сами значения в Git не попадают.

Безопасный шаблон без реальных значений:

```text
token: <BOT_ID>:<BOT_SECRET>
chat_id: -100<GROUP_ID>
```

`npm run dev` и `npm start` читают файл в Node-обёртке до запуска Worker и передают значения только как server-side bindings. Переменные `VITE_*` не используются. После изменения файла сервер нужно перезапустить.

Если файл отсутствует или неоднозначен, приложение продолжает обслуживать уже начатые тесты, но readiness возвращает `telegram_misconfigured`, а новые тесты блокируются. Для аварийного отключения доставки без остановки тестирования:

```powershell
$env:TELEGRAM_ENABLED='0'
npm run dev
```

Проверочное сообщение отправляется только явной командой:

```powershell
npm run telegram:test
```

Команда отправляет одно обезличенное сообщение с явной меткой теста. Она является внешним действием и не входит в `npm run verify`.

Для будущего Cloudflare deploy перенесите значения в secrets окружения (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) и не включайте `tg_token.txt` в deployment bundle. `TELEGRAM_ENABLED`, `TELEGRAM_REQUIRED`, `TELEGRAM_REPORT_MODE` и `TELEGRAM_CONFIG_STATUS=ready` — несекретные runtime-флаги. Для автономного outbox в cloud также понадобятся `MAINTENANCE_TOKEN` и Cron/внешний scheduler защищённого maintenance endpoint: локальная Node-обёртка там не запускается.

Режим отчётности задаётся до запуска приложения:

```powershell
$env:TELEGRAM_REPORT_MODE='progress_errors'
npm run dev
```

- `progress_errors` — обновляемая карточка, отдельные ошибки/таймауты и итог; режим по умолчанию;
- `summary` — только итог или сообщение о прерывании;
- `all_answers` — карточка, каждый ответ и итог; диагностический шумный режим.

## Telegram-outbox

Ответ, обновлённое состояние попытки и связанные outbox-события записываются одним D1 batch. Сначала бот отправляет корневую карточку кандидата, затем обновляет её через `editMessageText`; ошибки и таймауты приходят ответами на эту карточку. Правильные ответы в режиме `progress_errors` меняют только прогресс. UI переходит к следующему вопросу сразу и запускает flush в фоне.

Доставка имеет гарантию at-least-once. Стабильный event ID помогает распознать редкий дубль, если Telegram принял запрос, но ответ потерялся. Для одной группы сообщения сериализуются; 429 учитывает `retry_after`, временные ошибки получают backoff, а 400/401/403 переводят событие в `dead`. После успешной доставки текст payload очищается.

Локальная Node-обёртка запускает защищённый maintenance consumer каждые 50 секунд. Поэтому повторная доставка и 24-часовая очистка payload/имени не зависят от открытого Safari. Если компьютер был выключен, просроченные данные очищаются при первом maintenance-проходе после запуска. Browser flush остаётся ускоряющим механизмом, но не единственным consumer’ом.

Telegram-группа хранит персональные данные и эталонные ответы для ошибок. Эталон визуально скрывается спойлером, но остаётся доступен участникам группы. Группа должна быть закрытой, с минимальным составом администраторов. `protect_content` снижает риск случайной пересылки, но не защищает от администраторов и скриншотов.

## Банк вопросов

Администратор обновляет локальный `db/questions.json`; в Git хранится только `db/questions.example.json`. Если локального файла нет, runtime использует example-банк.

> `questions.example.json` и банк из ранней истории репозитория являются только демонстрационными: правильные ответы уже опубликованы в Git. Перед пилотом нужен новый непубликовавшийся банк с новыми ID. Простое удаление файла новым коммитом историю не очищает.

```powershell
npm run questions:validate
npm run questions:stats
```

Валидатор проверяет структуру, уникальность ID, размеры prompt/choices, difficulty, `correctIndex`, дубли, стартовую квоту и хотя бы один резервный remedial-вопрос в каждом пуле. Статистика выводится только локально и не раскрывается публичным API.

Вопросы с одинаковой проверяемой концепцией должны иметь общий необязательный `dedupeKey`, например `"dedupeKey": "windows-gpupdate"`. Сервер не включит два вопроса с одним ключом ни в базовую очередь, ни в remedial-добор после ошибки. Если ключ не задан, используется уникальный ключ на основе `id`.

Содержимое существующего `question.id` неизменяемо. Любое смысловое изменение формулировки, вариантов или правильного ответа требует нового ID; старую редакцию нужно перевести в `active: false`. При синхронизации рассчитывается SHA-256 revision всего банка и сохраняется в попытке.

## Восстановление попытки

Браузер хранит в `localStorage` только ID попытки, client `startKey`, token и срок жизни записи. Сервер хранит hash token и остаётся источником истины для таймеров, текущего вопроса и результата.

- потерянный ответ на стартовый запрос безопасно повторяется с теми же `startKey` и token;
- state/answer/flush запросы используют Bearer token и `Cache-Control: no-store`;
- сетевой запрос обрывается примерно через 8 секунд, локальная сессия при этом сохраняется;
- просроченный вопрос и общий лимит обрабатываются сервером;
- завершённая попытка открывается сразу на экране результата.

## Health и эксплуатация

- `GET /api/health/live` — процесс отвечает;
- `GET /api/health/ready` — схема, банк и обязательная Telegram-конфигурация готовы;
- health-ответы не содержат token, chat ID или другие секретные подробности.

Операционные команды:

```powershell
npm run ops:backup
npm run ops:backup:verify -- --from backups/<backup>.sql
npm run ops:retention
npm run ops:retention -- --apply
npm run ops:restore -- --from backups/<backup>.sql --apply
```

`retention` по умолчанию работает как dry-run. Apply и restore требуют остановленного приложения, создают и проверяют логический backup до изменения данных. Полный runbook находится в [`docs/operations.md`](docs/operations.md).

## Проверки

Главный quality gate:

```powershell
npm run verify
```

Он последовательно запускает secret scan Git index/изменённых/untracked non-ignored файлов, validation банка, unit/helper tests, TypeScript, ESLint, production build, scan build-артефактов, WebKit E2E в iPad portrait/landscape и production dependency audit.

`tg_token.txt`, `.dev.vars*`, локальный банк, D1 state и backups игнорируются Git. CI выполняет тот же `npm run verify` на Node.js 22.13.

## Архитектурные границы

Намеренно не реализованы:

- авторизация, роли, ATS и административная панель;
- Service Worker и полноценный offline-режим;
- AI-оценка, proctoring и anti-cheat;
- Redis, отдельный queue service, WebSocket и микросервисы;
- публичное размещение без дополнительного access-control слоя.

Текущая модель рассчитана на один доверенный локальный iPad. Публикация в сеть потребует аутентификации, rate limiting, origin/CSRF-защиты, документированной privacy policy и управляемых Cloudflare secrets. Подробный дальнейший план — в [`docs/roadmap.md`](docs/roadmap.md).
