# Candidate Check

Candidate Check — локальное iPad-first приложение для первичного технического отбора кандидатов. Интерфейс работает на React 19, API — в Cloudflare Worker runtime через Vinext, данные — в project-local SQLite-совместимой D1.

Версия 1.3.0 превращает управление банком в рабочее место администратора: добавлены справочник категорий, пакетные immutable-правки, импорт/экспорт с предварительной проверкой, атомарные черновики, матрица покрытия и очередь вопросов, требующих внимания. История тестов и уже начатые попытки при этом не переписываются.

- детерминированный JSON export только актуальных leaf-редакций без исторических дублей и секретов;
- черновики пакета изменений с CAS-публикацией одной ревизией или полным откатом при ошибке;

## Модель оценки

| Уровень | Базовых | Баллы за базовый | Баллы за дополнительный |
|---|---:|---:|---:|
| `easy` | 5 | 2 | 1 |
| `medium` | 7 | 4 | 2 |
| `hard` | 7 | 6 | 3 |
| `expert` | 1 | 20 | 10 |

Двадцать основных вопросов дают `baseMaxScore = 100`. Внутренние веса банка остаются неизменными; при расчёте базовый вопрос получает множитель `2`, дополнительный — `1`. Поэтому правильный дополнительный ответ возвращает только 50% стоимости основного вопроса той же сложности. Общий лимит — 10 дополнительных вопросов, итоговый score не может превысить 100.

Дополнительный вопрос создаётся только после ошибки или таймаута на основном вопросе и ставится после основной двадцатки. Ошибка на дополнительном вопросе не порождает новый remedial. Если уникального вопроса той же сложности нет, тест продолжается без ошибки и с меньшим числом дополнительных вопросов.

Verdict рассчитывается сервером:

- `PASS` → «Рекомендован»: score не менее 80 и accuracy не менее 70%;
- `REVIEW` → «К просмотру»: score не менее 50, но условия `PASS` не выполнены;
- `FAIL` → «Не рекомендован»: score меньше 50.

Точность рассчитывается по всем 20 основным и фактически заданным дополнительным вопросам. Старые завершённые попытки не пересчитываются; рейтинг показывает только совместимую 100-балльную когорту и не смешивает профили отбора.

## Быстрый запуск

Требуется Node.js 22.13+.

```powershell
npm install
Copy-Item db/questions.example.json db/questions.json
npm run questions:validate
npm run dev -- --port 3001
```

Откройте URL из вывода dev-сервера. Локальная D1 хранится в игнорируемом каталоге `.wrangler/`.

## Локальная административная аналитика

Для включения `/admin/login` создайте в корне игнорируемый файл `admin_pin.txt` с одной строкой из 6–12 цифр и перезапустите сервер. PIN читается только Node-обёрткой: Worker получает PBKDF2 hash/salt и отдельный случайный session secret, а клиентский bundle — ничего из перечисленного.

```powershell
Set-Content -LiteralPath admin_pin.txt -Value '<ЛОКАЛЬНЫЙ_PIN>' -NoNewline
npm run dev -- --port 3001
```

Сессия хранится в `HttpOnly; SameSite=Strict` cookie восемь часов. После пяти неверных попыток вход блокируется на 15 минут. Если файл отсутствует или некорректен, отключается только admin-раздел; тестирование кандидатов продолжает работать.

Exact-аналитика включает только попытки с `analyticsFactsVersion = 1`. Её когорта определяется сочетанием `scoringVersion + testConfigId + bankRevision + testProfileId`; `appVersion` используется только для диагностики. Фактические счётчики и доли отображаются при любом `n`, первичные статистические сигналы включаются с `n=30`, индекс качества — с `n=50`, discrimination — с `n=100`. Подробные формулы и правила интерпретации находятся в [`docs/analytics-metrics.md`](docs/analytics-metrics.md).

Вкладка «Банк вопросов» показывает canonical content и правильный вариант только внутри защищённой admin-сессии. Рабочие разделы «Вопросы», «Категории», «Импорт и экспорт», «Черновики» и «Контроль» позволяют подготовить пакет, увидеть diff и покрытие, а затем опубликовать его одной ревизией. Изменение темы, сложности, текста, контекста, вариантов, правильного ответа или `dedupeKey` создаёт новый ID и выключает предыдущую редакцию. Полный workflow и правила конкуренции описаны в [`docs/question-bank-admin.md`](docs/question-bank-admin.md).

Balanced profile включается отдельно после проверки shadow-метрики:

```powershell
$env:BALANCED_SELECTION_ENABLED='1'
npm run dev -- --port 3001
```

По умолчанию работает старый проверенный selector, а новый алгоритм только сохраняет `shadowCoverageScore`.

## Telegram-конфигурация

В корне нужен локальный `tg_token.txt`, содержащий ровно один bot token и ровно один групповой `chat_id` формата `-100…`. Подписи и пробелы допустимы, сами значения в Git не попадают.

Безопасный шаблон без реальных значений:

```text
token: <BOT_ID>:<BOT_SECRET>
chat_id: -100<GROUP_ID>
```

`npm run dev` и `npm start` читают файл в Node-обёртке до запуска Worker и передают значения только как server-side bindings. Переменные `VITE_*` не используются. После изменения файла сервер нужно перезапустить.

Если файл отсутствует или неоднозначен, приложение продолжает обслуживать уже начатые тесты, но readiness возвращает `telegram_misconfigured`, а новые тесты блокируются. Для аварийного отключения доставки без остановки тестирования:

```powershell
$env:TELEGRAM_ENABLED='0'
npm run dev
```

Проверочное сообщение отправляется только явной командой:

```powershell
npm run telegram:test
```

Команда отправляет одно обезличенное сообщение с явной меткой теста. Она является внешним действием и не входит в `npm run verify`.

Для будущего Cloudflare deploy перенесите значения в secrets окружения (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) и не включайте `tg_token.txt` в deployment bundle. `TELEGRAM_ENABLED`, `TELEGRAM_REQUIRED`, `TELEGRAM_REPORT_MODE` и `TELEGRAM_CONFIG_STATUS=ready` — несекретные runtime-флаги. Для автономного outbox в cloud также понадобятся `MAINTENANCE_TOKEN` и Cron/внешний scheduler защищённого maintenance endpoint: локальная Node-обёртка там не запускается.

Режим отчётности задаётся до запуска приложения:

```powershell
$env:TELEGRAM_REPORT_MODE='progress_errors'
npm run dev
```

- `progress_errors` — обновляемая карточка, отдельные ошибки/таймауты и итог; режим по умолчанию;
- `summary` — только итог или сообщение о прерывании;
- `all_answers` — карточка, каждый ответ и итог; диагностический шумный режим.

## Telegram-outbox

Ответ, обновлённое состояние попытки и связанные outbox-события записываются одним D1 batch. Сначала бот отправляет корневую карточку кандидата, затем обновляет её через `editMessageText`; ошибки и таймауты приходят ответами на эту карточку. Правильные ответы в режиме `progress_errors` меняют только прогресс. UI переходит к следующему вопросу сразу и запускает flush в фоне.

Доставка имеет гарантию at-least-once. Стабильный event ID помогает распознать редкий дубль, если Telegram принял запрос, но ответ потерялся. Для одной группы сообщения сериализуются; 429 учитывает `retry_after`, временные ошибки получают backoff, а 400/401/403 переводят событие в `dead`. После успешной доставки текст payload очищается.

Локальная Node-обёртка запускает защищённый maintenance consumer каждые 50 секунд. Поэтому повторная доставка, 24-часовая очистка payload/имени и controlled refresh устаревших analytics aggregates не зависят от открытого Safari. Analytics refresh объединяет завершения за 30 секунд и выполняется автоматически не чаще одного раза в 3 минуты; ручная кнопка остаётся fallback. Если компьютер был выключен, обслуживание возобновляется после следующего запуска. Browser flush остаётся ускоряющим механизмом, но не единственным consumer’ом.

Telegram-группа хранит персональные данные и эталонные ответы для ошибок. В сообщении об ошибке выбранный и правильный варианты видны сразу. Группа должна быть закрытой, с минимальным составом администраторов. `protect_content` снижает риск случайной пересылки, но не защищает от администраторов и скриншотов.

## Банк вопросов

При первом запуске пустой D1 банк загружается из локального `db/questions.json`; если файла нет, используется `db/questions.example.json`. После bootstrap рабочим источником истины становится D1, а дальнейшие изменения выполняются во вкладке «Банк вопросов». Перезапуск не откатывает их к JSON-файлу.

> `questions.example.json` и банк из ранней истории репозитория являются только демонстрационными: правильные ответы уже опубликованы в Git. Перед пилотом нужен новый непубликовавшийся банк с новыми ID. Простое удаление файла новым коммитом историю не очищает.

```powershell
npm run questions:validate
npm run questions:readiness
npm run questions:stats
```

Эти CLI-команды проверяют bootstrap-файлы, а не заменяют workflow управляемой D1-ревизии. Валидатор всегда проверяет публичный example-банк и дополнительно локальный банк, если он существует. Он контролирует структуру, уникальность ID, размеры topic/prompt/choices, difficulty, `correctIndex`, дубли, стартовую квоту и хотя бы один резервный remedial-вопрос в каждом пуле. `questions:readiness` безопасно показывает `READY / WARNING / NOT READY`, матрицу topic × difficulty и worst-case remedial reserve для legacy и balanced selector. Тексты, варианты и правильные ответы этот отчёт не выводит. D1-статистика также запускается только локально и не раскрывается публичным API.

Вопросы с одинаковой проверяемой концепцией должны иметь общий необязательный `dedupeKey`, например `"dedupeKey": "windows-gpupdate"`. Сервер не включит два вопроса с одним ключом ни в базовую очередь, ни в remedial-добор после ошибки. Если ключ не задан, используется уникальный ключ на основе `id`.

Для вопроса с командой, логом или конфигурацией можно передать необязательный технический контекст. `contextType` и `context` задаются только вместе; содержимое отображается как обычный текст либо безопасный preformatted-блок без интерпретации HTML:

```json
{
  "id": 1001,
  "difficulty": "medium",
  "topic": "Linux",
  "prompt": "Что произошло в журнале?",
  "contextType": "log",
  "context": "sshd[1842]: Failed password for invalid user admin",
  "choices": ["...", "..."],
  "correctIndex": 0,
  "active": true,
  "dedupeKey": "linux-sshd-failed-login"
}
```

Допустимые значения `contextType`: `text`, `code`, `command`, `log`, `config`. Контекст входит в неизменяемое содержимое вопроса, поэтому добавлять его к уже использованному ID нельзя — нужна новая редакция с новым ID.

Содержимое существующего `question.id` неизменяемо. Любое изменение формулировки, категории, сложности, вариантов, правильного ответа, контекста или `dedupeKey` выпускается как новая редакция с новым ID; старая сохраняется неактивной. Каждая операция атомарно рассчитывает SHA-256 revision всего банка, сохраняет membership snapshot и добавляет безопасную audit-запись.

## Восстановление попытки

Браузер хранит в `localStorage` только ID попытки, client `startKey`, token и срок жизни записи. Сервер хранит hash token и остаётся источником истины для таймеров, текущего вопроса и результата.

- потерянный ответ на стартовый запрос безопасно повторяется с теми же `startKey` и token;
- state/answer/flush запросы используют Bearer token и `Cache-Control: no-store`;
- сетевой запрос обрывается примерно через 8 секунд, локальная сессия при этом сохраняется;
- просроченный вопрос и общий лимит обрабатываются сервером;
- завершённая попытка открывается сразу на экране результата.

## Health и эксплуатация

- `GET /api/health/live` — процесс отвечает;
- `GET /api/health/ready` — схема, банк и обязательная Telegram-конфигурация готовы;
- health-ответы не содержат token, chat ID или другие секретные подробности.

Операционные команды:

```powershell
npm run ops:backup
npm run ops:backup:verify -- --from backups/<backup>.sql
npm run ops:backup:retention
npm run ops:retention
npm run ops:retention -- --apply
npm run ops:restore -- --from backups/<backup>.sql --apply
npm run analytics:explain
npm run analytics:benchmark
```

`retention` по умолчанию работает как dry-run. Raw backup/rollback-state автоматически ограничены TTL 24 часа; `ops:backup:retention` позволяет заранее увидеть число просроченных артефактов без вывода их имён, а `--apply` явно применяет очистку. Apply и restore требуют остановленного приложения, создают и проверяют логический backup до изменения данных. Полный runbook находится в [`docs/operations.md`](docs/operations.md).

## Проверки

Главный quality gate:

```powershell
npm run verify
```

Он последовательно запускает secret scan Git index/изменённых/untracked non-ignored файлов, validation банка, unit/helper tests, TypeScript, ESLint, production build, scan build-артефактов, WebKit E2E в iPad portrait/landscape и production dependency audit.

`tg_token.txt`, `.dev.vars*`, локальный банк, D1 state и backups игнорируются Git. CI выполняет тот же `npm run verify` на Node.js 22.13.

## Архитектурные границы

Намеренно не реализованы:

- многопользовательские роли, SSO и ATS-интеграция;
- Service Worker и полноценный offline-режим;
- AI-оценка, proctoring и anti-cheat;
- Redis, отдельный queue service, WebSocket и микросервисы;
- публичное размещение без дополнительного access-control слоя.

Текущая модель рассчитана на один доверенный локальный iPad. Публикация в сеть потребует аутентификации, rate limiting, origin/CSRF-защиты, документированной privacy policy и управляемых Cloudflare secrets. Подробный дальнейший план — в [`docs/roadmap.md`](docs/roadmap.md).
