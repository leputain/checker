# Candidate Check

Компактное локальное приложение для первичного технического отбора кандидатов. Интерфейс построен на React 19, серверная логика — на Vinext/Next-compatible API routes, данные хранятся в project-local SQLite-совместимой D1 базе.

Проект сознательно остаётся небольшим инструментом: без регистрации, ролей, ATS-функций, внешних сервисов и отдельной административной панели.

## Возможности v0.2

- старт теста без регистрации: кандидат вводит имя;
- общий серверный лимит 10 минут и серверный лимит 60 секунд на вопрос;
- случайная выборка из четырёх пулов сложности;
- детерминированное перемешивание вариантов отдельно для каждой попытки;
- правильный ответ и исходный порядок вариантов не передаются в браузер;
- за неверный ответ или таймаут добавляется ранее не использованный вопрос той же сложности;
- дополнительные вопросы влияют на accuracy и количество ошибок, но не увеличивают базовый score;
- серверный verdict: `PASS`, `REVIEW` или `FAIL`;
- восстановление активной попытки после reload через `sessionStorage`;
- идемпотентная повторная отправка ответа;
- анонимный рейтинг с учётом ошибок и времени;
- компактная статистика качества вопросов;
- JSON-банк вопросов с полями `difficulty`, `topic`, `prompt`, `choices`, `correctIndex`, `active`;
- адаптивный тёмный интерфейс для desktop и mobile.

## Модель оценки

| Уровень | Вес | Стартовая квота |
|---|---:|---:|
| Базовый (`easy`) | 1 | 2 |
| Средний (`medium`) | 2 | 2 |
| Сложный (`hard`) | 3 | 1 |
| Экспертный (`expert`) | 5 | 1 |

Шесть стартовых вопросов дают `baseMaxScore = 14`. Этот максимум фиксируется при создании попытки.

Баллы начисляются только за правильные ответы на базовые вопросы. Дополнительный вопрос помогает собрать больше наблюдений о кандидате, но не позволяет восстановить потерянные базовые баллы.

Verdict рассчитывается сервером:

- `PASS`: score не менее 70% от `baseMaxScore` **и** accuracy не менее 70%;
- `REVIEW`: score не менее 50% **или** accuracy не менее 60%;
- `FAIL`: всё ниже порога `REVIEW`.

Accuracy рассчитывается по всем фактически отвеченным вопросам, включая дополнительные.

## Рейтинг

Порядок сортировки:

```text
score DESC -> wrong_count ASC -> duration_seconds ASC
```

При равном score выше находится кандидат с меньшим количеством ошибок, затем — завершивший тест быстрее.

## Восстановление попытки

Браузер хранит в `sessionStorage` только `attemptId` и токен попытки. После reload клиент запрашивает актуальное состояние через `GET /api/attempts/:id`.

Источником истины остаётся сервер:

- таймеры не сбрасываются;
- новый вопрос не создаётся;
- уже обработанный ответ не начисляет баллы повторно;
- завершённая попытка открывается сразу на экране результата.

После завершения запись активной попытки удаляется из `sessionStorage`.

## Банк вопросов

Seed-банк находится в [`db/questions.json`](db/questions.json). Вес вычисляется автоматически по `difficulty`, поэтому в JSON его указывать не нужно.

Пример:

```json
{
  "id": 14,
  "difficulty": "medium",
  "topic": "security",
  "prompt": "Почему секреты нельзя хранить в Git?",
  "choices": ["...", "...", "...", "..."],
  "correctIndex": 1,
  "active": true
}
```

Поддерживаемые topic сейчас являются обычными строками: `general`, `backend`, `database`, `linux`, `network`, `security`, `architecture`. Отдельного справочника и CMS намеренно нет.

При старте приложения встроенные вопросы синхронизируются с локальной базой по `id`. Для расширения банка достаточно добавить объект в JSON и перезапустить dev-сервер.

## Статистика вопросов

Endpoint `GET /api/questions/stats` и модальное окно «Качество вопросов» показывают:

- количество ответов;
- количество правильных ответов;
- процент правильных;
- процент ошибок.

Это диагностический инструмент, а не полноценная аналитическая система. Значения имеют смысл только после накопления достаточного числа попыток.

## Локальный запуск

Требуется Node.js 22.13+.

```powershell
npm install
npm run dev
```

Откройте URL, который напечатает dev-сервер. Локальная база создаётся и обновляется автоматически в игнорируемом каталоге `.wrangler/`.


## Архитектурные границы

Намеренно не реализованы:

- авторизация, пользователи, роли и invite-ссылки;
- отдельная административная панель или визуальный редактор;
- UI-импорт JSON: текущего файла банка достаточно для локального сценария;
- Redis, очереди, WebSocket и микросервисы;
- AI-оценка, proctoring и anti-cheat;
- Docker/Kubernetes только ради запуска приложения;
- сложная матрица компетенций по topic.

## Возможный v0.3

- валидация JSON-банка отдельной командой перед запуском;
- экспорт рейтинга и статистики в CSV;
- фильтрация статистики по topic и сложности;
- настройка квот и таймеров через небольшой локальный конфигурационный файл;
- архивирование старых результатов и резервное копирование SQLite.

## Безопасность перед изменением границ эксплуатации

Текущая модель рассчитана только на локальное использование с одного доверенного устройства. Перед публикацией в сеть потребуются аутентификация административных функций, rate limiting, origin/CSRF-защита mutation API, политика хранения результатов и резервное копирование. Скрытая ссылка контролем доступа не является — это просто URL в плаще и шляпе.
